# DocPrep — stan trzech projektów i wspólny plan prac

**Stan audytu: 4 października 2026.** Zakres: `Backend`, `Frontend` (pacjent), `AdminFrontend` (recepcja i lekarz). Podstawą jest aktualny kod, w tym niezacommitowane zmiany frontendu pacjenta, oraz testy uruchomione podczas audytu. Ostatni commit w chwili sprawdzenia: `12fef01`.

Ten plik jest wspólną kolejką pracy. „Zaimplementowane” oznacza obecność w kodzie i podłączenie odpowiednich operacji; nie oznacza automatycznie potwierdzenia działania z rzeczywistym ElevenLabs, operatorem wiadomości i środowiskiem docelowym. Takie potwierdzenia mają osobne zadania.

**Aktualizacja po pracy równoległej nad MVP:** backend oraz oba fronty zostały spięte dla ścieżki panel → link → rzeczywisty czat ElevenLabs → import → edycja pól → jedno zatwierdzenie i udostępnienie → raport lekarza. Cały zestaw ma również wspólny Docker Compose i krótką instrukcję w głównym README. Serwer ogranicza listę i status wizyt do przypisanego lekarza; kolejka pokazuje rzeczywiste nazwisko i czas. Szczegóły odbioru, adresy uruchomionego systemu i pozostałe ograniczenia: [wspólny przepływ MVP](mvp-wspolny-przeplyw.md). Poniższa kolejka obejmuje także szersze prace poza tym pierwszym przebiegiem.

## 1. Ocena organizatora

**Trzy projekty mają już większość podstawowego procesu. Największa pozostała praca to domknięcie integracji i niezawodności, a także uzupełnienie panelu personelu.** Nie trzeba ponownie budować logowania, rozmowy, edycji raportu, zgód ani kalendarza.

| Projekt                      | Co już jest                                                                                                                                                                                                                       | Co przede wszystkim zostało                                                                                                                                                      |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Backend**                  | Wizyty, rezerwacje i kolizje, personel i konto pacjenta, ElevenLabs, import do draftu, wersje JSON/PDF, zgody, pytania lekarza, anulowanie i żądania usunięcia; serwerowy zakres wizyt lekarza i metadane kolejki.                | Poprawne scalanie sesji, trwałe ponowienia, rzeczywiste powiadomienia, dopracowanie raportu i eksploatacji.                                                                      |
| **Frontend — pacjent**       | Rzeczywiste konto i własne wizyty, publiczny link, głos/czat, karta wizyty, sprawdzenie i edycja raportu, obserwacje, jedno zatwierdzenie z udostępnieniem, cofnięcie zgody, PDF i odpowiedzi lekarzowi. Osobne demo pod `/demo`. | Wejście kodem i przez `/access`, dołączanie kolejnej zweryfikowanej wizyty do konta, pełny tryb bez agenta, odzyskiwanie po powrocie oraz konfiguracja transkrypcji dopowiedzeń. |
| **AdminFrontend — personel** | Rzeczywiste API i osobne demo, JWT/refresh, kalendarz/lista, tworzenie i zmiana rezerwacji, link bezpośrednio po utworzeniu, plan dnia lekarza z nazwiskiem i długością wizyty, wersje raportu/PDF i pytania.                     | Edycja katalogu i kont personelu, pełna edycja rezerwacji, historia zdarzeń, szczegóły dowodów obserwacji i operacje prywatności.                                                |

**Pierwsze decyzje robocze:** właścicieli przydzielać według projektu, nie według ekranów. Kontrakty wspólne zaczyna backend, a front dołącza po ustaleniu DTO. Nie dopisywać do sprintu nowych modułów, dopóki nie przejdzie jedna wspólna ścieżka recepcja → pacjent → lekarz → uzupełnienie.
